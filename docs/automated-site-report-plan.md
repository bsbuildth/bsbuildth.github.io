# แผนระบบอัปเดตรูปหน้างานอัตโนมัติ

## เป้าหมาย

บันทึกอัปเดตรูปหน้างานจากมือถือได้รวดเร็ว โดยระบุวันที่และข้อความสำคัญเมื่อมี โดยไม่สร้าง PDF และไม่เก็บไฟล์ภาพไว้ใน Firestore

## หลักการจัดเก็บ

| ส่วน | ที่เก็บ | เหตุผล |
| --- | --- | --- |
| ข้อความรายงาน, สถานะ, รายการรูป และลิงก์ | Firestore | ค้นหา แก้ไข และแสดงรายการได้เร็ว ใช้พื้นที่น้อย |
| รูปสำหรับแสดงในระบบ | Firebase Storage | อัปโหลดจากมือถือได้ปลอดภัย ควบคุมสิทธิ์ตาม Firebase Auth |
| รูปต้นฉบับเมื่อบันทึกอัปเดต | Google Drive | เป็นคลังงานของบริษัท แชร์และจัดโฟลเดอร์ตามโครงการ/วันที่ได้สะดวก |

ไม่บันทึกไฟล์ภาพหรือ Base64 ลง Firestore โดยเด็ดขาด

## รูปแบบการทำงาน

1. ผู้ดูแลเลือกโครงการ แล้วกด “อัปเดตรูปหน้างาน”
2. ระบบตั้งวันที่ปัจจุบันให้แก้ไขได้ และเลือกรูปจากกล้องหรือคลังรูป
3. ใส่ข้อความสำคัญได้ตามต้องการ เช่น งานที่ทำ, ปัญหา, หรือสิ่งที่ต้องติดตาม
4. ระบบบีบอัดรูปในเครื่องเป็น WebP ก่อนอัปโหลด พร้อมสร้างภาพตัวอย่างขนาดเล็ก
5. บันทึกข้อมูลอัปเดตและ metadata ของรูปใน Firestore
6. ส่งรูปต้นฉบับเข้าโฟลเดอร์ Google Drive ของโครงการตามวันที่ แล้วเก็บเฉพาะภาพตัวอย่างใน Storage
7. หน้าภาพรวมแสดงอัปเดตล่าสุดและปุ่มเปิดอัลบั้ม Drive ของแต่ละโครงการ

## โครงสร้าง Drive

`BS Build / โครงการ / YYYY-MM ชื่อโครงการ / อัปเดต-YYYY-MM-DD /`

ในแต่ละอัปเดตมี `01-ภาพหน้างาน.jpg`, `02-ภาพหน้างาน.jpg` และรูปอื่นตามลำดับที่เลือก โดยข้อความสำคัญเก็บในระบบคู่กับอัลบั้มนี้

## ข้อมูลอัปเดต

`siteUpdates/{updateId}` เก็บเฉพาะข้อมูลต่อไปนี้:

- `projectId`, `projectName`, `updateDate`, `status` (`draft`, `uploading`, `saved`, `failed`, `archived`)
- `note` สำหรับข้อความสำคัญ ซึ่งเว้นว่างได้
- `photos[]`: ชื่อไฟล์, caption, ลำดับ, thumbnail URL, Storage path, Drive file ID, สถานะส่ง
- `driveFolderId`, `createdBy`, `createdAt`, `updatedAt`
- `operationId` สำหรับกันการส่งซ้ำเมื่อแตะบันทึกซ้ำหรือเครือข่ายหลุด

อัปเดตหนึ่งรายการมีสถานะเดียวที่ผู้ใช้เห็น: ร่าง, กำลังส่ง, บันทึกแล้ว, ส่งไม่สำเร็จ หรือเก็บเข้าคลัง ส่วนแต่ละรูปมีสถานะ `queued`, `processing`, `done`, `failed` เพื่อกดส่งซ้ำเฉพาะรูปที่ผิดพลาดได้

## ข้อจำกัดเพื่อคุมพื้นที่และค่าใช้จ่าย

- รับเฉพาะ JPG, HEIC, PNG และ WebP; แปลงเป็น WebP ก่อนส่ง
- จำกัดรูปต้นฉบับ 12 MB ต่อรูป และไม่เกิน 20 รูปต่ออัปเดต
- ภาพแสดงในระบบกว้างไม่เกิน 1,920 px; thumbnail กว้าง 480 px
- ลบไฟล์อัปโหลดที่ไม่ผูกกับรายงานภายใน 24 ชั่วโมง
- หลังย้ายไป Drive สำเร็จ เก็บใน Firebase Storage เฉพาะภาพตัวอย่างที่ย่อกว้าง 480 px เป็นเวลา 15 วัน แล้วลบอัตโนมัติ; Google Drive เป็นที่เก็บรูปต้นฉบับเพียงชุดเดียว
- ลบอัปเดตต้องยืนยัน 2 ขั้น และย้ายไฟล์ Drive ไปถังขยะก่อน ไม่ลบถาวรทันที
- ตัดข้อมูลตำแหน่ง GPS และ metadata กล้องออกก่อนอัปโหลด เพื่อไม่เผยตำแหน่งบ้านโดยไม่จำเป็น
- ตรวจพื้นที่ Drive ก่อนเริ่มส่ง และแจ้งจำนวน/ขนาดรูปที่เลือกให้ผู้ใช้เห็น

## งานอัตโนมัติ

- เมื่อบันทึกอัปเดต: สร้างโฟลเดอร์วันที่บน Drive, ส่งรูป, และบันทึกลิงก์กลับมา
- รายสัปดาห์: สรุปจำนวนอัปเดตของแต่ละโครงการและอัปเดตล่าสุด
- ทุกงานใช้ `operationId` เดียวตลอดการส่งและกดทำซ้ำได้ เพื่อไม่ให้ส่งรูปซ้ำเมื่อเน็ตหลุด
- งานสรุปรายสัปดาห์เป็นเพียงข้อมูลในหน้าผู้ดูแล ไม่ส่งข้อความหรืออีเมลอัตโนมัติจนกว่าจะเปิดใช้ภายหลัง

## ความปลอดภัย

- หน้าเว็บคุยกับ Firebase Storage ด้วย Firebase Auth และ Storage Rules เท่านั้น
- การสร้างโฟลเดอร์/อัปโหลดเข้า Drive ทำผ่านบริการฝั่งเซิร์ฟเวอร์ที่ตรวจ Firebase ID token ก่อนเสมอ; ห้ามใส่ OAuth client secret หรือ service-account key ใน GitHub Pages
- จำกัดสิทธิ์เฉพาะผู้ดูแล และเก็บ audit log สำหรับการย้าย, ลบ และแชร์ไฟล์
- เริ่มจากโฟลเดอร์ Drive ที่ `bsbuildth@gmail.com` เป็นเจ้าของและแชร์ให้ทีมเท่าที่จำเป็น
- ไม่สร้างลิงก์สาธารณะอัตโนมัติ; เปิดรูปในระบบเฉพาะผู้ดูแล และใช้สิทธิ์ของโฟลเดอร์ Drive ตามที่เจ้าของกำหนด

## การใช้งานบนมือถือ

- ปุ่มหลักคือ “ถ่ายรูป” และ “เลือกรูป”; รองรับการเลือกรูปหลายรูป
- แสดงภาพตัวอย่างทันที, วันที่, จำนวนรูป และช่องข้อความสำคัญช่องเดียว
- บันทึกร่างในเครื่องก่อนเริ่มส่ง เพื่อให้กลับมาทำต่อได้หลังโทรศัพท์ถูกปิดหรือเน็ตขาด
- แสดงความคืบหน้ารายรูป, ปุ่มส่งซ้ำ, และปุ่มเปิดโฟลเดอร์ Drive เมื่อสำเร็จ
- หน้ารายการค้นหาตามโครงการและวันที่ เรียงอัปเดตล่าสุดก่อน

## เงื่อนไขพร้อมเริ่มสร้าง

1. เปิดใช้ Firebase Storage และ deploy Storage Rules สำหรับ `site-updates/{updateId}`
2. สร้างบริการฝั่งเซิร์ฟเวอร์สำหรับ Drive พร้อมตรวจ Firebase ID token
3. ตั้งโฟลเดอร์หลักใน Drive ของ `bsbuildth@gmail.com` และเก็บเฉพาะ folder ID ในค่าตั้งระบบ
4. ทดสอบด้วยรูปจริง 1, 10 และ 20 รูป รวมถึงกรณีออกจากหน้า/เน็ตหลุดระหว่างส่ง
5. ตรวจว่าส่งซ้ำ, ลบ, เก็บเข้าคลัง และเปิด Drive ได้ตรงกับรายการในระบบ

## สัญญาการเชื่อม Drive

หน้าเว็บเรียก `VITE_DRIVE_BRIDGE_URL` ด้วย Firebase ID token และส่งเพียง `updateId` กับ `operationId` บริการฝั่งเซิร์ฟเวอร์ต้องอ่านรายการรูปจาก Firestore, คัดลอกไฟล์ต้นฉบับจาก Firebase Storage เข้าโฟลเดอร์ Drive และตอบกลับ `{ folderId, driveUrl }` เท่านั้น หลังได้รับผลสำเร็จ หน้าเว็บลบต้นฉบับชั่วคราวจาก Firebase Storage ทันที โดยเหลือภาพตัวอย่างถึงวันหมดอายุ 15 วัน

## ลำดับการสร้าง

1. เพิ่มโครงการและหน้า “อัปเดตรูปหน้างาน” แบบมือถือ
2. เพิ่มอัปโหลดรูปแบบบีบอัด, preview, เลือกภาพ, ลบ และเรียงลำดับ
3. เพิ่ม Firestore schema, Storage Rules และหน้ารายการอัปเดต
4. เชื่อมบริการ Drive และการส่งรูปเมื่อบันทึกอัปเดต
5. เพิ่มงานสรุปรายสัปดาห์, audit log และทดสอบการกู้คืน

## ข้อเสนอที่แนะนำ

ใช้ Firebase Storage สำหรับช่วงที่กำลังส่งรูป และ Google Drive เป็นคลังรูปตามโครงการและวันที่หลังบันทึกอัปเดต วิธีนี้ทำให้ระบบเร็วบนมือถือ, Firestore ไม่บวม, และเจ้าของงานเข้าถึงรูปจาก Drive ได้ง่ายโดยไม่ต้องสำเนาภาพไว้สองที่ตลอดไป
