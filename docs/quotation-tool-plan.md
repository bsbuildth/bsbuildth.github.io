# แผนสร้างเครื่องมือใบเสนอราคา BSBuildTh

สถานะ: สร้าง MVP และตรวจในเครื่องแล้ว ยังไม่ได้เปิดใช้กับ Firebase production หรือเผยแพร่
เอกสารอ้างอิง: QT-03_Kitchen_Renovation_Supaporn.pdf ที่ผู้ใช้ให้ อ่านภาพครบ 1 หน้า A4
ขอบเขตคำขอ: อัปเดตแผนและเตรียมสร้างเครื่องมือ ข้อความใน PDF เป็นข้อมูลตัวอย่าง ไม่ใช่คำสั่งปฏิบัติงาน

## สถานะการพัฒนา

สร้าง editor, ตัวอย่าง A4, การคำนวณสตางค์, draft/issued/void, เลขเอกสารไม่ซ้ำ, revision snapshot และ private Firestore Rules แล้ว ชุดทดสอบยืนยันยอดอ้างอิงและ PDF ภาษาไทยทั้งหนึ่งหน้า/หลายหน้า ดู [แผนงานหลัก](project-plan.md) และ [ผลตรวจล่าสุด](validation-current.md) ก่อนใช้ข้อมูลลูกค้าจริงยังต้องตั้ง admin claim ให้ `bsbuildth@gmail.com` และ deploy Rules ด้วยบัญชีที่มีสิทธิ์โปรเจกต์ `bs-build`

## เป้าหมายและตำแหน่งในโปรเจ็กต์

เพิ่มเมนู “ใบเสนอราคา” ในระบบผู้ดูแลเดิม ใช้ React และ Firebase Auth/Firestore ที่มีอยู่ รองรับผู้รับเหมากรอกข้อมูลลูกค้า แบ่งหมวดงาน คำนวณยอดและงวดชำระ ดูตัวอย่าง A4 แล้วพิมพ์/บันทึก PDF ภาษาไทย

เริ่มจากเครื่องมือภายในสำหรับผู้ดูแล ไม่ผูกกับราคาในเครื่องคำนวณหน้าเว็บโดยอัตโนมัติ เพราะราคาประเมินกับใบเสนอราคาที่ออกจริงมีรายละเอียดและเงื่อนไขต่างกัน การนำคำขอจาก contacts มาเป็นร่างทำได้ในระยะต่อไปโดยผู้ดูแลตรวจข้อมูลก่อน

## สิ่งที่ต้องรองรับจากตัวอย่าง

| ส่วน | ข้อกำหนด |
| --- | --- |
| หัวเอกสาร | ชื่อผู้เสนอราคา/ธุรกิจ คำอธิบายบริการ โทรศัพท์ เลขเอกสาร วันที่ |
| ข้อมูลคู่ค้า | ชื่อลูกค้า เบอร์โทร ชื่อโครงการ ผู้เสนอราคาและเบอร์ติดต่อ |
| ตารางงานหลัก | หมวดงาน ลำดับย่อย รายละเอียด จำนวน หน่วย ราคา/หน่วย ยอดรายการ |
| อุปกรณ์เพิ่มเติม | แยกจากงานหลัก ระบุว่าเป็นราคาประมาณการและลูกค้าซื้อเองได้ |
| รายการแถม | แสดงราคาอ้างอิงขีดฆ่า ป้าย FREE และยอดเรียกเก็บ 0.00 |
| สรุป | ยอดงานหลัก ยอดอุปกรณ์ที่รวมในข้อเสนอ ยอดรวมทั้งหมด |
| รายละเอียดงาน | ขอบเขตงาน ขนาด วัสดุ สิ่งที่รวม/ไม่รวม และเงื่อนไขโปรโมชั่น |
| งวดชำระ | เปอร์เซ็นต์ จำนวนเงิน เงื่อนไขแต่ละงวด และฐานยอดที่ใช้คำนวณ |
| ท้ายเอกสาร | หมายเหตุ ระยะรับประกัน ช่องลงชื่อสองฝ่ายและวันที่ |

ตัวอย่างมีหมวดเคาน์เตอร์ครัว ระบบไฟฟ้า และพื้นห้องครัว ใช้จำนวนทศนิยมและหน่วย งาน/ตร.ม./ชุด/จุด/ช่อง เครื่องมือต้องเพิ่มหมวดและหน่วยได้ ไม่ล็อกให้ใช้เฉพาะงานครัว

## กติกาคำนวณที่ต้องชัดเจน

1. จำนวน × ราคาต่อหน่วย = ยอดรายการ ปัดครึ่งขึ้นเป็น 2 ตำแหน่งด้วย decimal arithmetic; จัดเก็บเงินเป็นสตางค์และจำนวนเป็น decimal string เพื่อไม่ใช้ floating point คำนวณเงินโดยตรง
2. งานหลักในตัวอย่างรวม 55,010.00 บาท จาก 6,750 + 6,080 + 10,480 + 9,000 + 900 + 1,800 + 20,000
3. อุปกรณ์เพิ่มเติมที่คิดเงินจริงรวม 44,500.00 บาท จาก 9,000 + 4,000 + 13,500 + 3,000 + 15,000
4. ค่าแรงติดตั้งที่แถมมีราคาอ้างอิง 4,500.00 บาท แต่ยอดเรียกเก็บเป็นศูนย์ ห้ามบวกยอดนี้แล้วหักซ้ำ
5. ยอดรวมตัวอย่าง = 55,010 + 44,500 = 99,510.00 บาท อุปกรณ์แต่ละรายการมีตัวเลือก “รวมในใบเสนอราคา” หรือ “ลูกค้าจัดหาเอง”; รายการที่ลูกค้าจัดหาเองแสดงแยกและไม่รวมยอดเรียกเก็บ
6. ฐานงวดชำระตั้งค่าได้ระหว่าง “ยอดงานหลัก” และ “ยอดรวมที่เรียกเก็บ” และต้องระบุชื่อฐานใน PDF ตัวอย่างใช้ยอดงานหลัก: 40% = 22,004; 40% = 22,004; 20% = 11,002 บาท ไม่ใช้ 99,510 เป็นฐานโดยปริยาย
7. เปอร์เซ็นต์งวดต้องรวม 100%; ปัดงวดก่อนหน้าเป็นสตางค์แล้วให้งวดสุดท้ายรับส่วนต่าง เพื่อให้ยอดงวดรวมเท่าฐานทุกครั้ง
8. เอกสารตัวอย่างไม่แสดง VAT หรือส่วนลดทั้งเอกสาร รุ่นแรกจึงไม่เพิ่มภาษีหรืออ้างว่ารวม/ยกเว้นภาษีอัตโนมัติ หากต้องการภาษีต้องกำหนดกติกาเพิ่มก่อนใช้งานนั้น
9. วันที่เก็บเป็น YYYY-MM-DD แสดงปี พ.ศ. ตามรูปแบบตัวอย่าง; ไม่เปลี่ยนวันที่อ้างอิงในเอกสารให้เป็นวันที่ปัจจุบันโดยอัตโนมัติ

## ขั้นตอนใช้งานรุ่นแรก

1. เปิดรายการใบเสนอราคา: ค้นหาตามเลขเอกสาร ลูกค้า โครงการ สถานะ; สร้างใหม่หรือทำสำเนา
2. กรอกข้อมูลเอกสาร ลูกค้า โครงการ และผู้เสนอราคา
3. เพิ่มหมวดและรายการ ใส่จำนวน/หน่วย/ราคา ลากจัดลำดับ หรือเลือกรายการตัวอย่างที่แก้ไขได้
4. แยกอุปกรณ์เสริมและรายการแถม ดูยอดรวมปรับทันที
5. ตั้งงวดชำระ ขอบเขตงาน การรับประกัน และหมายเหตุ ตรวจฐานคำนวณให้ชัด
6. บันทึกร่างโดยมีสถานะกำลังบันทึก/บันทึกสำเร็จ/ผิดพลาด เก็บข้อมูลไว้เมื่อเครือข่ายล้มเหลวและเตือนก่อนออกเมื่อมีข้อมูลยังไม่บันทึก
7. ดูตัวอย่าง A4 และตรวจยอดก่อนกดออกเอกสาร การออกเอกสารสร้าง revision ที่แก้ย้อนหลังไม่ได้; การแก้ไขภายหลังสร้าง revision ใหม่พร้อมเหตุผล
8. พิมพ์หรือบันทึก PDF ผ่านหน้าต่างพิมพ์ของเบราว์เซอร์ รุ่นแรกใช้วิธีนี้เป็นค่าเริ่มต้น ไม่เรียกว่าดาวน์โหลด PDF อัตโนมัติ; ปุ่มดาวน์โหลดตรงเป็นงานเพิ่มหากต้องการ

การส่งอีเมล/LINE การลงนามอิเล็กทรอนิกส์ การรับเงิน และลิงก์เอกสารสาธารณะอยู่นอก MVP ไม่ส่งเอกสารให้ลูกค้าอัตโนมัติ

## โครงสร้างข้อมูลและสิทธิ์

- quotations/{id}: schemaVersion, documentNumber, documentDate, status (draft/issued/void), revision, sellerSnapshot, customerSnapshot, project, sections, terms, paymentPlan, totals, createdBy, updatedBy, createdAt, updatedAt
- sections: id, title, kind (main/optional), order, items
- items: id, description, quantity, unit, unitPriceSatang, isFree, includedInQuote, referenceUnitPriceSatang, order
- paymentPlan: base (main/total), installments [{label, percentage, condition}], calculatedAmountsSatang
- quotations/{id}/revisions/{revisionId}: snapshot ที่ออกเอกสารแล้ว รวมผู้จัดทำ เวลาออกเอกสาร เวอร์ชันแม่แบบ และยอดที่คำนวณ ไม่อ้างชื่อ/ราคาแบบสดที่เปลี่ยนตามข้อมูลธุรกิจภายหลัง
- quotationNumberReservations/{normalizedNumber}: จองเลขเอกสารใน transaction เดียวกับการออกเอกสาร ป้องกันสองแท็บออกเลขซ้ำ ใช้เลขร่างภายในแยกจากเลขเอกสาร; รุ่นแรกกรอกเลขเองได้แบบ QT-03 และตรวจซ้ำ ระบบเลขอัตโนมัติรายเดือน/ปีเป็นงานถัดไป
- privateQuotationTemplates/{id}: ข้อมูลผู้เสนอราคา เงื่อนไขและหมวดงานมาตรฐานที่ไม่มีข้อมูลลูกค้า

ให้เฉพาะ admin อ่าน/เขียนใบเสนอราคาและข้อมูลลูกค้า ผู้ใช้ทั่วไป/ผู้ไม่ล็อกอินต้องเข้าถึงไม่ได้ ทดสอบ Rules ทั้ง parent และ subcollections ใช้ deny-by-default; ห้ามเพิ่ม collection ลงกลุ่ม public read เดิม และต้องแก้การตรวจ admin ก่อนใช้งานข้อมูลจริง

การออกเอกสารต้องออนไลน์เพื่อทำ transaction; ล็อกการแก้ issued snapshot ด้วย Rules ไม่พึ่งปุ่ม disabled เท่านั้น ป้องกันเขียนทับงานจากอีกแท็บโดยตรวจ revision/update version เมื่อต้องออกเอกสาร หากมีระบบรับเงินหรือส่งอัตโนมัติในอนาคตให้ย้ายการตรวจยอดสำคัญไปบริการที่เชื่อถือได้

ห้ามบรรจุ PDF ต้นฉบับ ชื่อ/เบอร์ลูกค้าจริง หรือภาพหน้าเอกสารลง app/public, fixture หรือ Git เนื่องจาก repository เป็นสาธารณะ ใช้ลูกค้าและโครงการสมมติในชุดทดสอบ คงเฉพาะโครงสร้างและตัวเลขที่ใช้ตรวจคำนวณ

## หน้าจอและไฟล์ที่สร้างแล้ว

- app/src/pages/Quotations.jsx และ Quotations.css: รายการ ค้นหา ทำสำเนา editor สถานะการบันทึก และงานพิมพ์
- app/src/components/QuotationPreview.jsx: เอกสาร A4 และสถานะ draft/void
- app/src/lib/quotation.js: ฟังก์ชันคำนวณด้วยสตางค์และ validation
- app/src/firebase/quotations.js: CRUD, transaction, revisions
- app/src/App.jsx: route /admin/quotations แยกโหลดตาม route พร้อม admin guard
- app/firestore.rules: สิทธิ์ส่วนตัวและ revision immutability

ทุกส่วนใช้หน่วยเงินและกติกาปัดเศษร่วมกันทั้งฟอร์ม ตัวอย่างพิมพ์ และข้อมูลที่บันทึก ไม่คำนวณยอดแยกหลายชุด

## ข้อกำหนด PDF และการพิมพ์

- A4 แนวตั้ง โทนน้ำเงิน ตารางเส้นบาง และกล่องข้อมูลตามตัวอย่าง ใช้ฟอนต์ไทยที่รองรับและมีสิทธิ์ใช้งาน
- ยึดหนึ่งหน้าเมื่อข้อมูลสั้น แต่รองรับหลายหน้าโดยไม่ย่อจนอ่านยาก; ซ้ำหัวตารางทุกหน้า ไม่ตัดแถวกลางข้อความ และไม่แยกบล็อกงวดชำระ/ลายเซ็นอย่างไม่เหมาะสม
- ชื่อ/คำอธิบายยาวต้องตัดบรรทัดได้ จำนวนเงินชิดขวา 2 ตำแหน่ง ชื่อหมวดและป้ายรายการแถมต้องอ่านได้แม้พิมพ์ขาวดำ
- ซ่อนปุ่มและเมนูเมื่อพิมพ์ รอโหลดฟอนต์ก่อนพิมพ์ ตรวจ margin และ header/footer ของเบราว์เซอร์
- ช่องลายเซ็นใน MVP เป็นช่องว่างสำหรับลงนาม ไม่มีการคัดลอกลายเซ็นบุคคลจากเอกสารต้นฉบับ
- เลขหน้าอัตโนมัติที่ควบคุมได้และไฟล์ PDF เหมือนกันทุกอุปกรณ์ต้องประเมิน renderer เพิ่ม ถ้าการทดสอบ browser print ไม่ผ่านเกณฑ์ ให้เลือก renderer และทดสอบภาษาไทยก่อนรับรองฟีเจอร์ดาวน์โหลดตรง

## แผนดำเนินงานและเกณฑ์รับงาน

### ระยะ 1: ฐานระบบและแบบฟอร์มทดลอง

แก้ admin authorization และเพิ่ม Rules tests; สร้าง calculation module พร้อม unit tests; ทำ editor/preview ด้วยข้อมูลสมมติก่อนผูก production เกณฑ์ผ่าน: กรณีตัวอย่างได้ 55,010 / 44,500 / 99,510 และงวด 22,004 / 22,004 / 11,002 ตรงทุกจุด

### ระยะ 2: บันทึกและออกเอกสาร

เชื่อม Firestore แบบส่วนตัว เพิ่ม draft/duplicate/revision/void และการจองเลข เกณฑ์ผ่าน: สองแท็บออกเลขเดียวกันไม่ได้ บันทึกล้มเหลวไม่ล้างข้อมูล เอกสารที่ออกแล้วไม่เปลี่ยนเมื่อแก้ราคาแม่แบบ

### ระยะ 3: พิมพ์และตรวจรับ

ตรวจ A4 1 หน้าและ 3 หน้า ข้อความไทยยาว รายการ 0 บาท อุปกรณ์ลูกค้าจัดหาเอง และทศนิยม; ทดสอบ responsive editor, build, lint เฉพาะงานใหม่และ regression ที่เกี่ยวข้อง เกณฑ์ผ่าน: ยอด preview/ข้อมูล/PDF ตรงกัน ไม่มีตัวอักษรหายหรือตารางล้น และข้อมูลไม่ปรากฏใน public bundle

### ชุดทดสอบสำคัญ

- จำนวน 7.6 × 800 = 6,080; จำนวนติดลบ/ว่าง/NaN/รูปแบบไม่ถูกต้องถูกปฏิเสธ
- รายการฟรี 4,500 คิดยอด 0; สลับ “ลูกค้าจัดหาเอง” แล้วยอดรวมเปลี่ยนถูกต้อง
- เปลี่ยนฐานงวดงานหลัก/ยอดรวม; เปอร์เซ็นต์ไม่ครบ 100 ต้องออกเอกสารไม่ได้; เศษสตางค์ไปงวดสุดท้าย
- ลูกค้าสมมติชื่อยาวและรายละเอียดหลายบรรทัดไม่ทับยอดเงิน
- ผู้ไม่ล็อกอินและผู้ใช้ทั่วไปอ่าน/เขียน quotations และ revisions ไม่ได้
- ไม่ออกเอกสารเมื่อข้อมูลจำเป็นไม่ครบหรือบันทึกล่าสุดยังไม่สำเร็จ

## ค่าเริ่มต้นสำหรับเริ่มพัฒนา

ใช้เครื่องมือภายใน Admin, บาทไทย, รูปแบบวันที่ไทย, เลขเอกสารกรอกเองพร้อมกันซ้ำ, พิมพ์/บันทึก PDF ผ่านเบราว์เซอร์, ไม่เพิ่มภาษีอัตโนมัติ, ไม่ส่งลูกค้าอัตโนมัติ รายละเอียดธุรกิจและเงื่อนไขทุกอย่างแก้ไขได้ต่อเอกสาร

ก่อนใช้งานจริงต้องยืนยันผู้มีสิทธิ์ออกเอกสาร ข้อมูลผู้เสนอราคาที่ใช้จริง รูปแบบเลขเอกสาร และเงื่อนไขภาษีถ้าต้องมี โดยไม่ขวางการสร้างรุ่นทดลองด้วยข้อมูลสมมติ
